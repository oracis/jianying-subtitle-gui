## 1. 背景与问题

把一段**长音频**（播客、讲书、访谈，20~60 分钟）做成视频，最耗时的不是剪辑，是**字幕**。

现有路径都不理想：

| 方案 | 问题 |
|---|---|
| 剪映原生「识别字幕」 | 要手工点、逐条改；分段不合理（按 ASR 断句而非语音停顿）；不能批量；不能脚本化 |
| 剪映 + 手工打轴 | 27 分钟音频要几小时 |
| 通用 ASR 工具（Whisper 命令行） | 输出 SRT 要手工导入剪映，还要自己配时间轴 |
| 云端字幕服务 | 要上传、要付费、隐私顾虑 |

**核心矛盾**：ASR 本身不难，难的是「**按真实语音停顿切成符合字幕规范的小段，并直接落到剪映草稿箱**」这一段脏活。

---

## 2. 目标与非目标

### 目标

1. **拖进去就出结果** —— 把音频拖到窗口，不需要任何命令行或配置，结束时剪映草稿箱里已有一个可直接编辑的草稿
2. **分段贴近原生体验** —— 字幕边界落在**真实语音停顿**上，而不是按 ASR 的粗断句或固定字数硬切
3. **画布/路径自动适配** —— 自动探测剪映安装目录与草稿箱目录，支持横屏/竖屏
4. **安装包小** —— 模型不打包进 exe，运行时按需下载
5. **批量可用** —— 提供无 GUI 的命令行模式，便于脚本化处理多个文件

### 非目标（明确不做）

- 不做视频剪辑、不含转场/特效/BGM
- 不做字幕翻译、不做得不到说话人分离
- 不替代人工校对 —— 定位是**粗剪**，产出需要人工过一遍

## 6. 质量指标（当前实测）

以 27.75 分钟讲书音频为基准（本机 i7-6600U：**2 物理核 / 4 逻辑线程**，无独显）。
下表 RTF 为**批量推理（batch=8）**下的实测值：

| 模型 | RTF | 全片耗时 | 准确率（人耳抽检） | 繁体残留 |
|---|---|---|---|---|
| tiny | 约 0.065 | 约 1.8 分 | 差（"毒贩"→"讻伴"） | 有 |
| base | **0.094** | **2.83 分** | 中（"毒贩"→"读犯"，"可卡因"→"科卡因"） | 已由 zhconv 修掉 |
| small | 约 0.29 | 约 8 分 | 较好（"毒贩"正确，偶有错字） | 已由 zhconv 修掉 |
| medium | 1.56（2026-10-22 实测） | 46 分 | 较好（90 秒样本 5~8 处错） | 已由 zhconv 修掉 |

> **本机性能上限**：`cpu_threads=2` 时并行度已达 1.73x，两个物理核压满。
> RTF 0.094 就是这台机器的天花板，本地路径没有数量级优化空间。
> 详细基准与放弃方案见 `ARCHITECTURE.md`。

**分段质量**（base 模型 + 批量推理，452 条字幕）：

| 指标 | 值 |
|---|---|
| 字幕条数 | 452 |
| 平均时长 | 3.28s |
| 中位时长 | 3.11s |
| 最长 | 6.68s |
| 字级单元 | 6309 |
| 时间轴异常 | 0 |
| 边界落在真实停顿 | 由算法保证（v2 算法实测 100%） |

**⚠️ 已知质量缺口**：中文识别准确率不足（base 错字明显），且存在繁体输出。这是当前最大短板，见 §8。

## 7. 模型策略（含待决策项）

### 7.1 已确定的决策

**模型不打包进 exe**，首次转换时按需下载到：

```
%LOCALAPPDATA%\JianyingSubtitle\models\faster-whisper-<档位>\
```

理由：
- exe 体积从 ~500MB 降到 12MB
- 可随时换档位，不必重新打包
- 只用一次的用户不必为 484MB 买单

### 7.2 开放决策：默认档位该选哪个？

**用户的质疑（成立）**：既然模型不占 exe 体积，为什么默认选 base 这种中间档？

约束条件（本机实测）：

| 约束 | 实际情况 |
|---|---|
| CPU | 4 核 |
| GPU | Intel HD 520 核显，**无 CUDA** |
| 唯一硬约束 | **速度**（体积已不是约束） |

候选方案：

| 方案 | 默认档位 | 优点 | 缺点 |
|---|---|---|---|
| A | base（现状） | 3.4 分钟，快 | 错字多、繁体，质量最差 |
| B | small | 质量明显更好 | 10 分钟 |
| C | medium | 质量接近可用 | 预计 20~25 分钟（待测） |
| D | **让用户选，默认 small** | 尊重用户权衡 | 需要 UI 说清耗时 |

**倾向方案 D**：默认 `small`，同时在 UI 里把每档的「预计耗时」直接算出来显示（按音频时长 × RTF），让用户自己决定质量/速度平衡。

理由：
- 用户抱怨的核心是**质量**（分段太长 → 其实是识别质量和分段共同导致）
- 「粗剪」允许有错字，但繁体+大量错字会让校对成本超过自己打字
- 明确显示耗时后，用户不会觉得被隐瞒

**实测补充（2026-10-22）**：medium RTF 1.56（29.5 分钟音频 46 分钟）、large-v3-turbo RTF 1.45
（但中文准确率反不如 medium）。结论：本机（2 核 4 线程）不存在「又快又准」的档位，
medium 已按速度下架，见 v0.11。

### 7.3 模型档位规格（拟）

| 档位 | 体积 | RTF（4核实测/估算） | 27分钟音频 | 定位 |
|---|---|---|---|---|

## 8. 关键风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **中文识别准确率不足** | 字幕需大量人工修订，价值打折 | 扩档位 + 繁转简 + 术语词表（F14/F15/F20） |
| **无 GPU，大模型太慢** | 质量与速度不可兼得 | UI 明示耗时，让用户选；检测到 NVIDIA 时启用 GPU |
| **剪映索引被覆盖** | 草稿「消失」 | 生成前强制关闭剪映（已实现） |
| 剪映版本升级导致 JSON 结构失效 | 草稿打不开 | 骨架模板独立存放，便于替换；自检覆盖结构校验 |
| ffmpeg 缺失/shim 损坏 | 无法解码 | 随包分发 + 候选实跑验证（已实现） |
| 模型下载失败 | 首次使用阻塞 | 多源回退（hf-mirror → 官方），断点续传 |

## 9. 验收标准

MVP 判定为「可用」需同时满足：

1. 拖入 27 分钟音频，无人工干预产出草稿
2. 剪映能正常打开该草稿，音频轨与字幕轨时间轴正确
3. 字幕边界落在真实语音停顿上（自动化校验 ≥ 99%）
4. 时间轴异常（重叠/负时长）为 0
5. 草稿箱中可见，且不与旧草稿重名冲突
6. 全过程有进度反馈，失败有可读错误信息

当前：1/2/4/5/6 已满足；**3 由算法保证但「3 的语义正确性」依赖识别质量**；识别准确率是本版本最大缺口。
